12. 組語 evaluate：四個 16-bit 數的算術式

題目描述解題思路範例追蹤完整程式碼與解釋易錯點自我檢查

01 / 題目到底要做什麼？

由 C 呼叫 PIC18 組合語言函式 evaluate，計算 a op1 b op2 c op3 d。函式宣告必須是 extern unsigned int evaluate(unsigned int a, char op1, unsigned int b, char op2, unsigned int c, char op3, unsigned int d);。四個數字是16位元無號整數，三個運算子是8位元字元，只支援 +、-、*。乘法優先於加減，同優先序由左至右；例如 2+3×4−5=9。題目保證所有需要的中間結果與最後結果都在0–65535，不需要負數表示。最終 unsigned int 回傳值須放在 C 的 ans，於 Watches 展示；題目稱 evaluate.asm，此專案實際用 evaluate.S。目前 main.c 的式子是 50−20−10×2，並不是 README 仍描述的 2+3×4−5。

02 / 從題意推導程式

  1. 不必建堆疊或通用剖析器：維護一個尚未提交的乘法項 term、一個該項前的加減符號 sign，以及已提交的 total。初始化 total=0、term=a、sign=加。
  2. 依序讀三組 (op,rhs)。若 op 是乘法，就只做 term←term×rhs，不動 total 或 sign；因而連續乘法始終屬於同一項。
  3. 若 op 是加或減，先依原 sign 把整個 term 加進或減出 total，再將新 op 保存為下一項 sign，term 改為 rhs。舊 sign 必須先用完，不能先覆寫。
  4. 三個運算子都處理完後，仍有最後一項尚未提交，必須再 CALL eval_flush，才能把結果寫回 _evaluate$0 讓 C 取得。
  5. 16×16 乘法拆成低×低與兩個交叉乘積；只保留低16位，高×高項對低16位沒有貢獻。題目保證合法乘積不溢位，故省略高位計算不影響合法答案。
  6. 此 XC8 介面以 _evaluate$0 到 $6 連結符號傳入 a、op1、b、op2、c、op3、d，unsigned int 在各槽中低位在前。_evaluate$0 也作16位元返回槽；沒有硬編碼參數 RAM 位址。

05 / 最容易踩的坑

  • 支援的是 ASCII 字元 +、-、*，不是 HW4 分數題的0、1、2運算碼；C 呼叫必須使用單引號字元常數。
  • 若讀到減號立刻執行 total−rhs，就會把後續乘法拆錯；必須等乘法項完整才使用 pending sign。
  • 最後的 eval_flush 不可省略，否則只有前面幾項進 total，最後一個 term 完全遺漏。
  • 乘法只保留低16位，沒有額外溢位偵測；減法也以無號算術處理。超出題目保證的非法輸入可能回繞，不應當成有號運算或錯誤處理。
  • SUBWFB 中 C=1 表示前一位無借位；高位實際減的是 rhs.high+(1−C)，不是直接減 C。
  • README 中預設呼叫、ans=9 與歷史模擬結果已不等於目前 main.c 的測試式；本文只是依實際來源推導，未重新執行建置或模擬。
  • 工作區以靜態 COMRAM 配置，雖每次初始化狀態，但不具重入能力；中斷並行呼叫會破壞當前項與總和。

06 / 確認自己真的懂了

50−20−10×2 應是10還是40？

是10。先算10×2=20，再做50−20−20；把減法錯誤地結合成50−(20−20)或先整式左至右都不符合規則。

為何連續乘法不需要另一個優先序堆疊？

唯一高優先序運算是乘法，所有相鄰乘法都可累積在當前 term；遇加減再提交整項即可。

為什麼不用算 term.high×rhs.high？

這一項會乘上65536，只影響bit16以上，對16位元結果沒有貢獻；合法輸入的完整乘積又保證不超出16位元。

返回前是否仍可把 _evaluate$0 當作原 a？

不可；它在入口已複製到 term，返回時重用同一槽存結果，C 呼叫端應讀返回值而非假定原槽內容保留。
